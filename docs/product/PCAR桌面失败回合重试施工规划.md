## 一、从现有入口接入

桌面发送前已有可持久化的请求意图，受理后已有合批成员、回合快照和阶段恢复凭证。普通私聊另外保存实际使用的资料、每阶段模型回执和逐泡显示记录。界面已有失败状态行，可在原回合的失败行接入按钮。[桌面受理与恢复](修补包1-桌面消息受理与重启恢复规则.md) · [现有回合绑定](../../persona_runtime/desktop_recovery.py) · [私聊冻结资料](../../persona_runtime/ordinary_reply.py) · [界面失败状态](../../persona_runtime/workbench_web/persona_import.js)

现有通用 `retry` 的私聊分支尝试恢复原执行，其他部分会重读当前模型、角色和回复策略。本需求需要桌面专用的依据校验和冻结恢复。复用原受理、调度、阶段回执和呈现入口，按钮经桌面服务提交一次有归属的重试决定。[既有重试入口](../../persona_runtime/chat.py#L1140) · [服务路由](../../persona_runtime/server.py#L248)

## 二、冻结内容及恢复边界

| 时点 | 持久记录 | 恢复时如何使用 |
| --- | --- | --- |
| 每次发送前 | 原请求 ID、未改写的消息和顺序、明确引用及其版本、发送方式、会话和人物、原草稿版本。沿用本机发送意图的持久化入口。 | 首次发送结果丢失时，先按原请求 ID 查受理。已受理则接回原回合；确认尚未送出才交原意图给本机。相同请求 ID 始终对应相同载荷。 |
| 受理、封批时 | 将每个发送意图绑定到原批次。确认发送或滚动封批后，固定全部成员和顺序、历史读取边界、人物资料版本、会话与策略、模型用途与接收方、装配版本、引用及授权见证。保存验证所需的版本和指纹。 | 单发恢复一条原请求，合批恢复同一组消息。原批成员已在聊天记录中，只生成新的重试操作及物理尝试记录。后续新增消息、草稿、授权和世界库保留其真实进度。 |
| 各阶段首次派发前 | 冻结当时实际装配的阶段输入、前序回执和已选资料版本，以及输入指纹。前一阶段的输出尚未产生时，先保留所需的前序关系，等输入齐备再冻结。 | 已有可用回执的阶段直接继续。失败阶段按原输入指纹重新执行，后续阶段仍按原回合合同从新得到的有效结果推进。使用原阶段尚未撤回的资料。 |
| 原阶段结算后 | 保留历史尝试、已知及未知费用、工具原始结果、入库修订、发布编号和逐泡回执。 | 通过原回合与阶段编号复用已结算的操作。原有费用和回执永久可追溯，重试的新用量另记。已确定未显示的后续片可从原稿继续发布。 |

冻结的是该轮处理所需的数据和版本引用。用原业务记录、现有恢复合同和阶段回执重建，避免每次复制整库或复制凭据。重试时以当前授权为准核对实例、人物、会话、接收方和来源。已撤回、已变更或无法验证的原输入停止恢复，由现有授权或迁移入口处理。旧版本回合按实际保存的凭证判断资格，历史记录继续可读。

## 三、失败触发条件和按钮显示

1. **上游明确返回错误，立即判失败。** 以该阶段实际收到的 HTTP 错误、协议错误或模型接口的错误事件为依据。已收到完整结束回执却没有可用结果时，由现有协议校验记录明确错误。合同允许的空结果仍按正常结果处理。
2. **该阶段超过 180 秒仍无任何回复，判失败。** 从该阶段首次实际启动上游调用时计时，含当次建连。等待封批、排队、配额和气泡绘制各按原状态记录。HTTP 响应头、SSE 心跳和空帧只记运输进度。有实际模型内容、决策或可用工具结果时，按原流式与阶段规则推进。服务端保存起点和截止时间，窗口切换、重启及阶段内部重连沿用原截止。底层连接先超时且无明确上游错误时，按该阶段原 180 秒截止判定。超过时限的用时按 `elapsed > 180s` 比较。

这两个条件用于本轮**必需阶段**在当前路径无法完成时判定失败。已有有效降级答复时沿成功路径结算。180 秒衡量单个上游阶段的无回复等待，用于触发工作台失败状态和按钮。G-Auto 的整轮可见回复率继续按各自的观察期和可用工况对账。

按钮放在**该失败回合的状态行**。前端根据服务端失败版本显示，查前短句已经显示时保留原短句。显示「重试」与再次派发分开判定，点击后由服务查明旧尝试的状态。正在排队、仍在有效等待、已完成或用户已取消的回合沿原状态展示。

| 上游结果 | 服务端判定 | 工作台 |
| --- | --- | --- |
| 供应商已返回明确错误，或协议校验确认完整终态无可用结果 | 当场记录失败、原错误和用量。点击后复核该阶段是否已明确终结及重试限额和授权。认证或接收方问题先恢复对应配置与授权。 | 立即显示「重试」。 |
| 无回复超过 180 秒，且能证明未发送 | 记录失败和未发送证据。点击后解除旧执行占用，从原阶段派发。 | 超过 180 秒显示「重试」。 |
| 无回复超过 180 秒，原尝试是否被受理待核 | 记录用户可见的失败，并保留原物理尝试待核。点击后核对原回执。确认未发送或明确失败后可继续派发；找回有效结果直接沿原轮结算。仍待核则保留该状态和原用量。 | 超过 180 秒显示「重试」。点击后呈现核对进度，结果仍未知时保留待核反馈。 |
| 主回复已保存，气泡呈现未确认或剩余片尚未显示 | 按原气泡编号区分明确未显示和效果未知，沿原发布继续核对。 | 继续原呈现或显示已有的待核提示。 |

同一回合中任何**阻断正常交付**的上游阶段均采用这套判定。例如决策、取材译问、选材、出站范围复核、查前短答、联网工具、入库后复核、正文及实际启用的辅助模型。独立后台记忆任务继续沿自己的队列处理，确实阻断该回合的依赖纳入回合按钮。

180 秒是失败判据。能否再次派发依据原运输和业务回执独立判断。已经出站却丢失最终回执时，服务恢复连接后仍须取得原尝试可再次派发的证据。[阶段恢复证据](修补包1-桌面消息受理与重启恢复规则.md) · [上游与呈现判据](../acceptance/桌面无人值守-阶段0基线与验收矩阵.md#修补项与现场取证)

## 四、点击后的执行

1. 工作台提交同一回合、所见失败版本及本次点击的唯一操作 ID。界面暂时停用按钮，保持原消息和当前输入草稿。
2. 服务在同一写事务内校验归属、版本、失败证据、当前授权、配额以及是否已有执行者。以原回合和失败版本领取一次重试核对。双击、两个窗口同时点击、提交响应丢失和重开后重查均接回同一次受理。前端沿现有时间线刷新，回执核对和符合条件的模型执行在队列中异步进行。
3. 恢复冻结合批和上下文边界，从已证明可以重试的阶段开始。重新派发的阶段取得新的物理尝试 ID，开始新的 180 秒计时。成功、待核或已经产生可用结果的旧物理尝试原样留存。新尝试领取前找回有效旧回执时，按原结果结算。新尝试已领取后，迟到回执只按原凭证对账，不覆盖当前执行或重复入库、呈现。
4. 使用原回合定位发布结果。保留查前气泡、已确认正文前缀和已分享资料，避免重复显示。配置、历史和后续会话数据照常保留。某轮如果已经推进到其他对话，核对迟到结果是否仍能归原回合；归属或来源失效时，服务给出该轮无法安全恢复的原因。
5. 成功显示本轮应有的全部新气泡后收起按钮。再次明确失败时根据新失败版本重新判断。每次点击沿用现有的额度和自动恢复约束，单次点击的派发由服务侧幂等控制。

## 六、隔离实窗验收

**由验收代理在隔离 WebView2 工作台操作。** 使用当前正式装配的同版本程序、隔离数据和可控上游替身。代理从会触发相应分支的场景中选取一轮，先登记随机种子、该轮可以到达的模型阶段和故障类型，然后随机抽取**一个实际会执行的阶段**进行一次性注入。换场景重复抽样，直到下列角色每类有覆盖；随机未抽中的必要分支补一次定向验证。真实接收方的一次对照如有需要，另登记材料、用途和预算。隔离注入不需要关闭正式工作台或切断其服务。

| 场景 | 第一次注入与期待 | 恢复健康后的验收 |
| --- | --- | --- |
| 普通聊天 | 在 Jev、已启用的辅助模型或正文中抽一个。交替覆盖明确报错、已完成但无有效产出。 | 原失败轮出现「重试」。点击后再次派发失败阶段，其后尚未执行的阶段照常推进，角色气泡完整显示。 |
| 本地命中 | 在译问、选材或正文中抽一个，注入明确失败。 | 原问题和原来源继续使用。前序成功回执复用，公开工具新增派发为 0。 |
| 冷查询 | 在出站复核、查前短句、联网子步骤、入库后复核或正文中抽一个。覆盖一个已经显示查前消息或已经入库的样本。 | 解除注入后点击按钮。检查恢复从失败处继续，旧预告只显示一次，已完成的工具和入库没有重复，正文按原问题交付。 |
| 超过 180 秒无回复 | 分别模拟可证明未发出、已出站后无回复。用可控时间检查 180 秒及其后一刻，并用一次实窗确认 180 秒无回复后显示。分别检查仅收到响应头和心跳、180 秒以内已收到实际回复、窗口重开及并发迟到回执。 | 可证明未发出者解除注入后点击完成。原结果待核者也显示按钮，点击后重复查看、重开和恢复服务，证明原待核尝试零重放。再提供明确失败或有效原回执，验证安全派发或接续呈现。 |
| 连续发送与合批 | 一轮由多条原消息组成，失败后保留新草稿。并行测试两个窗口点击、重试受理回执丢失和同一服务重开。 | 原消息 ID、顺序、引用和批次一致，只有一笔有效重试受理，草稿及后续消息不受影响。 |
| 授权撤回、配置变更和迟到回执 | 失败后撤回所用来源或变更接收方；也验证原阶段迟到的响应和已有气泡的情况。 | 过期按钮即使被点击，服务也拒绝越权派发。迟到响应不覆盖新结果。已保存正文且仅剩呈现欠账时，模型新增派发为 0。 |
| 正常状态反例 | 正常回复、合法空结果、正在自动恢复、已经成功、用户已取消。 | 相应回合没有「重试」按钮，模型及呈现沿原流程。 |

每个可再次派发的场景依次核对**原失败回合出现按钮、解除故障、点击一次、同一消息和回合、失败阶段有新尝试、最终有效回复取得完整显示**。对结果未知的超时，单独核对按钮显示、回执核对与零重放。留存随机种子、实际阶段、注入位置、调用起点和截止、失败和重试操作编号、输入指纹、前后物理尝试计数、已知及未知用量和气泡回执。通过标准还包括原用户消息重复数、已成功或未知阶段重放数、重复入库及重复显示数均为 **0**，后继正常聊天可完成。

这组人工点击用来验收**失败后的用户补救**，按故障注入专项独立记账。G-Auto 正常及可自动恢复工况继续按原矩阵核对零管理介入。经证实的真实上游故障另记外部受阻，仍检查原请求是否保留以及恢复后能否接续。[G-Auto 对账](../acceptance/G-AUTO-总验收对账-20261122.md#r04-回执和计量)

## 七、工程交接

桌面发送和封批时登记回合所属实例、人物、会话、接收方及授权版本。执行时关联冻结输入和阶段回执，点击通过桌面管理接口受理。成功回执和已显示片段继续使用原编号。相同失败版本在两个窗口被点击时，只取得一次再次派发资格。对已经点击且仍待核的尝试，迟到的有效原结果直接结算，迟到的明确失败可接续已登记的点击。回合完成或取消后释放普通正文生成所用的临时输入副本。[阶段计时与重试](../../persona_runtime/desktop_turn_retry.py) · [桌面失败状态行](../../persona_runtime/workbench_web/persona_import.js)

隔离工程用例覆盖普通正文、可选角色选材、私聊并行决策、译问、出站复核、查前与查后正文、指定查询失败和入库后选材。测试核对原回合与消息顺序、冻结输入、已完成查询的复用、重复点击、权限撤回、首次有效内容、迟到回执和 180 秒边界。工作台服务入口另以隔离本机请求检查受理和权限，按钮用本地界面替身检查显示和点击。[工程用例](../../tests/test_desktop_turn_retry.py) · [角色选材和用量对账](../../tests/test_generation_retry.py) · [按钮渲染和点击](../../tests/workbench_retry_render.cjs)

经作者批准，两个独立 Windows WebView2 实例分别完成实窗验收。种子 161 抽中 J3，替身返回 HTTP 503，阶段从开始到记录失败用时约 0.113 秒。种子 170 在正文阶段保持静默，记录失败时的实际用时刚超过 180 秒。静默用例先观察到「重试」，再让原尝试返回明确终态，然后点击「重试」。两例各受理一次原消息，各确认一次重试，替换尝试沿用相同的原回合和冻结输入，其他已成功阶段没有重复派发。每轮 4 个气泡均有独立显示回执，两个实例均释放所属组件。实测使用受控上游替身，公网模型调用为 0。

本机私有验收目录的 `real-window-retry-acceptance.json` 保存逐轮对账。复测入口为 `python -B -m tests.workbench_private_daily_cycle <新隔离目录> --retry <随机种子> error`，末项可替换为 `silence`。正式服务调用与正式部署按作者决定执行。[实窗演练入口](../../tests/workbench_private_daily_cycle.py)
