# PCAR 版本、发布与公告管理规则

**状态**　作者已审定并授权启用，自 2026-11-24 起生效。

## 一、版本分工

| 类型 | 用途 | 交付方式 |
| --- | --- | --- |
| 内部开发版 | 新功能研发与测试、缺陷排查和修复、架构重构、性能优化及集成验证 | 使用源码、开发环境与验收记录 |
| 正式版 | 向用户交付经过作者验收并批准发布的功能与修复 | Windows 安装程序和 Android APK |

原来的「正式版」从本规则生效起归入内部开发版。已有公开版本按原编号保留。Windows 和 Android 的公开安装包统一归入正式版，既有的安装身份、签名和用户数据目录继续用于覆盖升级。

内部开发期间按改动规模灵活调整版本号。每次交接至少记录内部版本、源码提交和验收结果，便于定位故障和回退。需要验证安装或升级时，由作者先确认该批内部改动已经达到打包条件，再从冻结的源码构建**正式版候选包**。候选包用于核验安装与升级，通过后进入正式发布。

## 二、正式版版本号

正式版采用 `x.y.z`，三段均为非负整数。同一次发布包含不同级别的变更时，按最高级别升号一次。

| 升号 | 适用范围 | 编号规则 |
| --- | --- | --- |
| `z` 补丁 | 作者或社区测试者反馈的局部缺陷修复，例如焦点、显示、单个操作或局部兼容问题。影响可限定在原流程内，用户数据和主要使用方式可沿用 | `x.y.z → x.y.(z+1)` |
| `y` 次版本 | 已验收的用户功能更新、影响核心流程的严重缺陷修复、正式打包阶段发现的安装或升级问题，以及与功能和兼容性直接相关的架构调整 | `x.y.z → x.(y+1).0` |
| `x` 主版本 | 产品形态或核心使用方式的重大变化，或者影响广泛、需要独立迁移与兼容安排的架构更新 | `x.y.z → (x+1).0.0` |

以 `1.1.2` 为例，局部显示修正可编号为 `1.1.3`，经过验收的联网功能更新可编号为 `1.2.0`，双方确认的重大产品更新可编号为 `2.0.0`。升号依据用户受影响的范围、主要流程的变化和升级成本。反馈来源另行记录。

Codex 按规则判断 `y` 和 `z`，同步更新发布记录并注明归类理由。涉及升 `x` 时，由 Codex 与作者共同确认变更范围、迁移方式和发布理由，取得作者明确授权后再升号。每次正式发布仍须作者确认发布范围与验收结果。

## 三、跨平台命名和版本同步

- 正式版对用户显示 `PCAR x.y.z`。建议发行标签为 `pcar-vx.y.z`，同一批次的 Windows 和 Android 附件放在同一个 Release。
- 建议使用清楚区分平台和架构的文件名，例如 `PCAR-1.2.0-Windows-x64-Setup.exe` 与 `PCAR-1.2.0-Android-arm64.apk`。版本号以安装包内声明与发布清单为准。
- 同批交付同一项更新时，两端使用同一个 `x.y.z`。单平台修复可以单独发布，Release、下载入口和公告明确适用平台。另一端继续提供自己的最新可用包，下次双端发布直接对齐新的正式版本号。
- Windows 安装器文件版本可写作 `x.y.z.0`。Android 的 `versionName` 使用 `x.y.z`，`versionCode` 在每次可覆盖安装的构建中使用更大的整数，并在发布记录里登记。内部运行时版本和数据库结构版本单独记录。
- 正式发行的标签和安装包校验值固定。已发布程序需要修改时，按改动规模升号发布。下载入口指向 GitHub Release 中已核验的实际附件。

## 四、从内部验收到正式发布

1. **确认本批变更。** 作者确认要发布的功能、缺陷修复、适用平台和验收结果。Codex 记录版本号及升号理由，冻结用于打包的源码提交。
2. **构建并验包。** 核对界面、安装包、更新公告和发布清单的版本一致。按本批实际改动验证首次启动、适用的覆盖安装与旧数据读回，以及本批涉及的功能。核验安装包校验值和签名（适用时）。如有迁移或兼容条件，随包提供用户可执行的说明。
3. **确认公开发布。** 作者确认候选包和发布范围后，发布正式包、更新公告、版本说明与校验值，再核对公开下载、项目主页和使用指南。将获批作为主下载入口的正式 Release 设为 Latest。单平台发行时，主页同时保留另一平台的可用下载入口。
4. **处理发布后问题。** 核对受影响的平台和版本。作者可批准撤下有问题的附件或将下载入口切回上一可用版，公告同步说明影响范围和处理方式。修复包按规则另行升号。涉及数据迁移时，以已核验的回退方式指导用户。

发布清单至少记录正式版本、适用平台、源码提交、附件及校验值、验收结论、公告编号。跨端发布可使用不同的源码提交，各自绑定到实际安装包。

## 五、首次启动公告和公告中心

### 更新弹窗

- 正式版首次成功打开首页后，展示当前版本的更新公告。新安装和升级都适用。跳过多个版本时先展示当前版本，较早版本可从「公告」查看。
- 弹窗列出版本、日期、适用平台、用户能感受到的变化，以及影响使用的安装或迁移事项。提供「知道了」和「查看公告」。关闭或进入公告后记录已读，同一版本后续启动沿用已读状态。
- 公告随安装包提供，首次离线启动也能展示。公告读取失败时保留首页入口，用户可稍后从公告中心重试。

### 首页「公告」

- 正式版首页提供固定的「公告」入口，展示历史版本更新和作者发布的通知。按时间排列，可按「版本更新」「作者通知」筛选。每条保留稳定编号、发布日期和适用平台，便于定位和更正。
- 作者通知的内容与公开范围由作者确认，通知按独立编号发布，程序升号跟随功能和修复。建议以随包公告提供离线基础内容，通过项目官方发布源补充历史公告和独立通知，并缓存已读内容。读取公告无需模型 Key，客户端只拉取公开公告内容。
- 普通通知进入公告列表。确需在首次启动提醒的重要通知，由作者指定适用版本和期限，按通知编号记录已读。公告更正保留原编号，列表标注更正时间。

## 六、实施顺序

1. 审定本文件，确认跨平台版本同步策略与正式包命名。
2. 接入正式版的版本来源、发布清单、随包更新公告和首次启动弹窗。
3. 实现首页公告中心、历史公告、已读状态与独立通知更新。
4. 用一个正式版候选批次验收安装、升级、跳版本、离线启动、重复启动和公告查看，再按本规则公开发布。
