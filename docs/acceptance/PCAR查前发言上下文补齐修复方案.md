# PCAR 查前发言上下文补齐修复方案

作者已提供最终 System 原文并批准施工。修复已接入开发版，当前候选待实窗体验。实窗中，用户已经提出完整问题，查前模型却回复「好的，请提出你的问题」。生成回执显示，查前请求只包含角色提示和阶段、模式、篇幅字段。主回复有自己的完整输入和呈现回执。

## 设计

查前发言和主回复共享同一个角色、会话、当前用户请求及查证对象的工程归属。查前模型承担本轮承接与进度告知，主模型承担查证后的答复。两次生成各自留存请求与呈现回执，工具仍在查前气泡完整显示后派发。

进入查前阶段时，程序核对本轮 J4、资料缺口、合法公开查询和会话授权。从当前回合已冻结的来源组装薄上下文，再把状态与生成任务明确送进查前模型。

| 模型可见部分 | 内容和边界 |
| --- | --- |
| 人物 `persona` | 角色名和单独审阅过的相关性格、表达片段。首个候选复用验收角色现有角色卡里与承接消息、简短表达和语气有关的原文。每项绑定档案修订及片段位置。相关人物信息装在数据区，共用任务指令只承担本轮任务。 |
| 必要上下文 `context` | 当前用户至多三段相关原文，每段至多 80 字。优先使用实际公开任务所引用的当前消息，再取 J1 选定的当前对象，按原顺序装配。对齐长度时优先取已定位的原话范围。省略对象时可以附一段已授权且可核对的引用或关联的可见回复片段，至多 100 字。本轮已冻结的公开查询单列。 |
| 当前情境 `situation` | 用户请求已受理、公开查证准备就绪、此时还没有结果。三项来自冻结回执及阶段条件。 |
| 生成任务 | 按审阅稿的系统原文，自然接住已经发生的交流，用一条很短的角色回复表达接下来会去查以及对请求的自然回应。 |
| 输出要求 `output_constraints` | 首版沿用一泡、一句、最多 24 字和纯文本角色正文的合同。查证结果由后续的主回复提供。 |

有可用公开查询时，即使部分上下文缺失，查前模型也能收到当前情境及已核准的查询。人物片段、当前原话或引用权限有变化时须重新核验来源。查前模型的接收范围按本版待审样例核定。首批范围是验收角色的隔离工作台与现有角色资料。完整模型输入和接收方在私有审阅件逐项列出。

## 施工步骤

1. **冻结审阅件。** 绑定系统原文、人物字段选择、可见对话范围、场景字段、Flash 接收方及用途。作者批准后登记新的查前输入版本。旧已发送请求继续使用自己的版本和回执。
2. **接入同回合装配。** 在 `OrdinaryReply.write` 的查前分支复用 `_snapshot`、本轮选定对象和已冻结的查询。在生成前锁定输入片段、来源修订、授权和请求指纹，并在派发前复核。受理、人物版本、查找范围与回执归属均沿用该回合。
3. **更新查前请求合同。** 在 `ReviewedPrivateChatProviders._reply` 按审定版本验证字段结构及接收方，套用新的任务原文。所需人物片段与当前上下文跟随同一角色快照。保持纯文本、现行轮次和篇幅检查。
4. **沿真实呈现放行工具。** 查前发言完整显示后才取得派发资格。发送前中断可在同一绑定下确认续做。已有响应或外发效果未知时沿原尝试对账。查后的主回复接收实际查证状态和有效证据。
5. **验收。** 先用结构标识和保存的原回执检查装配与复核，再在隔离工作台使用作者批准的原话。结果分别保存 Flash 输出、窗口气泡、后续工具和主回复，交作者判断自然度。

## 验收清单

| 场景 | 要看见的结果 |
| --- | --- |
| 原现场合并的三条消息 | 查前发言接住已提出的查询，明确接下来要查。主回复承接它并交付实际结果。逐字新稿与窗口显示一致。 |
| 用户一句话提出新查证 | 首条角色短回复接住具体任务，角色口吻成立。 |
| 提到前文对象的补查 | 能从获准的引用或冻结查询接住对象。上下文范围和来源可在回执核对。 |
| 本地已足够、普通闲聊或本轮只查本地 | 沿原路由正常交付，公开工具派发为零。 |
| 查前尚未完整显示、中断、撤回或权限变化 | 工具没有越过原显示与权限门槛。旧回执保持可追溯，重复动作计数为零。 |

工程验收看输入、授权、可见先后顺序及调用次数。口吻和“有没有接住上一句”由作者在实际窗口审阅。

## 施工核对

开发版新增查前上下文装配。生成前重核角色版本、冻结公开任务和授权，保存当前输入片段范围、装配指纹及实际请求指纹。原现场只读重建中，System 与作者给出的原文逐字一致，User 数据与前版审阅样例一致，包含三条本轮原话和已核准的公开查询。离线复验覆盖查前尚未显示时公开工具派发为零，以及重开后沿原回合完成查证与正文交付。候选装配和核验回执存于本机私有验收目录。当前实窗仍需作者验收生成口吻。
